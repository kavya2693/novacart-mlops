# NovaCart

A mid-sized online retailer has three questions it asks every week. Which active
customers are about to stop buying, so retention can reach them first? How much
will we sell next month, so purchasing can reorder without overstocking? And
which products and customer groups actually drive the business? Each question
usually gets its own notebook, built by a different person, and each one looks
fine until it has to answer a live request.

The hard part is rarely the model. A churn model that scores 0.99 offline has
usually seen the future: its label leaked into its features. A model that was
right in the notebook drifts in production because the serving code computes
features slightly differently from the training code. A forecast that beats last
year looks good until someone checks it against a naive "same day last week"
guess. None of these failures show up in a single accuracy number.

This repository builds all three systems on one simulated company ("NovaCart",
4,000 customers, 62,904 orders) and wires them into a small production stack: a
feature service, a model registry with stage promotion, four HTTP APIs, drift
monitoring, a Helm chart and a load benchmark. The key decision is that features
are computed by a single module used by both training and serving, and a test
proves the two paths give the same numbers.

The data is synthetic, so the results show the engineering holds together, not
that these models would work on a real retailer.

## Results

From one run of `make pipeline` with the default seed:

| System | Metric | Result |
|---|---|---|
| Churn (logistic regression) | ROC-AUC / PR-AUC, 25% holdout, base rate 0.444 | **0.795 / 0.744** |
| Churn benchmark (gradient boosting) | ROC-AUC | 0.772 |
| Demand: LightGBM | MAPE / WAPE, last 60 days held out | **6.28% / 6.31%** |
| Demand: ARIMA(2,1,2) | MAPE / WAPE | 6.29% / 6.20% |
| Demand: seasonal-naive baseline | MAPE / WAPE | 7.50% / 7.45% |
| Knowledge graph | nodes / edges | 4,308 / 225,168 |

Two of these went against the expected story. The gradient-boosted churn model
did *worse* than plain logistic regression, so the simpler, fully explainable
model is the one in production. And LightGBM only ties ARIMA: it wins on MAPE by
0.01 points and loses on WAPE. On an aggregate series this smooth, the extra
machinery buys almost nothing over a classical model; both beat the naive
baseline by about 1.2 points.

The churn AUC of ~0.80 is deliberately not higher. The label is generated by a
noisy renewal process, so a near-perfect score would mean leakage, not skill.

### Serving under load

From `reports/slice2_kubernetes.md` (single-node kind cluster, 2 vCPUs,
1,500 requests):

| Configuration | Throughput | p50 | p95 |
|---|---|---|---|
| prediction=1, feature=1 | 73.0 req/s | 214 ms | 303 ms |
| prediction=3, feature=1 | 73.7 req/s | 212 ms | 298 ms |
| prediction=3, feature=3 | 157.0 req/s | 138 ms | 302 ms |

Tripling the prediction service changed nothing, because every prediction makes
a synchronous call to the feature service. Scaling the feature service instead
gave 2.15x the throughput. The bottleneck was not the service named on the
endpoint.

## How it fits together

```
 data_engine ─▶ SQLite/Postgres ─┬─▶ feature_pipeline ─▶ feature_store ─▶ training ─▶ Registry ─┐
                                 │                                                              │
                                 ├─▶ graph/build_graph ─▶ KG ─▶ analytics + CLV ─▶ Graph-RAG API (8103)
                                 │                                                              │
                                 └─▶ forecasting ─▶ LightGBM/ARIMA/naive ─▶ forecast API (8104)  │
                                                                                                ▼
   prediction-service (8102)  ──HTTP──▶  feature-service (8101)                       monitoring (PSI)
```

- **Churn** (`novacart/training`, `novacart/serving`). Features are computed
  strictly before the reference date; the label is the strictly-forward 30 days;
  customers inactive for 90 days are excluded rather than labelled "not churned".
  The prediction service fetches features over HTTP and returns a probability,
  the top five signed contributions, and the model version.
- **Demand forecasting** (`novacart/forecasting`). Daily company-wide demand
  (the dataset code also builds per-category series, but only the total is
  trained), three models compared on a time-based backtest, the winner
  registered and rolled forward 365 days, plus a reorder-point endpoint.
- **Graph-RAG** (`novacart/graph`). Orders become a customer-product-category
  graph. PageRank, Louvain communities, centrality and SVD embeddings run on it,
  plus RFM-based CLV segments. A question is parsed into an intent, mapped to a
  graph query (the equivalent Cypher is returned for transparency), answered by
  deterministic retrieval, and returned with citations. An `llm` hook can take
  over the prose without touching retrieval.
- **Monitoring** (`novacart/monitoring`). PSI per feature against frozen
  training bins. With no live traffic, the default run applies a synthetic shift
  to show the detector firing; it is a demonstration, not a measurement.

## Run it

```bash
make venv          # python venv + pinned deps
make pipeline      # data -> features -> churn -> graph -> forecast -> drift
make serve         # four APIs on ports 8101-8104
make test          # pipeline, then pytest (11 tests)
```

```bash
curl localhost:8102/predict/42
curl -XPOST localhost:8103/ask -H 'content-type: application/json' \
     -d '{"question":"top influential products"}'
curl 'localhost:8104/forecast?horizon=30'
curl localhost:8104/replenishment
```

The pipeline takes about 45 seconds on a laptop. `docker compose up` runs the
same services against Postgres and an MLflow server; `deploy/helm/novacart`
holds the Kubernetes chart used for the load test.

## Limitations

- **Synthetic data is the biggest gap.** The generator defines the behaviour the
  models recover, so every number above is an upper bound on what real data
  would give.
- **One snapshot.** Churn is trained on a single reference date with a
  stratified split, not rolling-origin backtests across time.
- **Forecasts are aggregate.** Company-wide demand over 4,000 customers is
  smooth, which flatters MAPE. SKU-by-store series would be far
  noisier. The 365-day forecast is a recursive roll, so error compounds.
- **The intent router is rule-based.** It is deterministic and testable but only
  understands the question shapes it was written for.
- **No graph database.** The graph runs in networkx. Cypher is generated for
  display; nothing here loads it into Neo4j or Neptune.
- **The registry is file-based** locally (MLflow-shaped, because MLflow had no
  wheels for the Python version used). Docker Compose swaps in real MLflow.
- **Load numbers come from a 2-vCPU VM.** Relative comparisons hold; absolute
  throughput does not transfer.

Per-model detail is in `MODEL_CARD.md`.
